# Первый пакет задач

Этот файл содержит 5 практических задач для самостоятельного изучения брокера сообщений RabbitMQ на базе вашего микросервисного полигона.

## 🛠️ Задача 1. Изучаем базовый обмен: «Асинхронный логер»
**Цель:** Понять разницу между отправкой сообщения напрямую в очередь и через обменник (Exchange), а также освоить паттерн *Publish/Subscribe*.

### Сценарий:
1. `SenderApi` при каждом входящем HTTP-запросе отправляет текстовое сообщение (лог) в RabbitMQ.
2. Используется тип обменника **Fanout Exchange** (он дублирует все сообщения во все привязанные к нему очереди).
3. Создаются два независимых консольных приложения-воркера:
   * **Воркер А (Файловый):** сохраняет полученные логи в локальный `.txt` файл.
   * **Воркер Б (Консольный):** просто выводит логи в консоль красивым цветом.

### Чек-лист реализации:
- [X] В `SenderApi` настроено объявление обменника (например, `logs-exchange`) с типом `ExchangeType.Fanout`.
- [X] Создан Воркер А, который при старте объявляет свою уникальную очередь и привязывает её к `logs-exchange`.
- [X] Создан Воркер Б, выполняющий аналогичную привязку со своей уникальной очередью.
- [X] Запущены оба воркера одновременно. При отправке одного сообщения из API оба воркера успешно его обработали.

### ❓ Вопросы для самопроверки:
* Что произойдет с сообщениями, если отправить их в Fanout Exchange, когда ни один воркер (и ни одна очередь) еще не запущены?
* Зачем воркерам использовать разные имена очередей в этой задаче?

## 🛠️ Задача 2. Изучаем умную маршрутизацию: «Региональные заказы»
**Цель:** Разобраться, как доставлять сообщения только определенным сервисам без ручной фильтрации на стороне потребителя.

### Сценарий:
1. `SenderApi` принимает заказы и отправляет их в **Topic Exchange** (например, `orders-exchange`).
2. Каждое сообщение снабжается ключом маршрутизации (`Routing Key`) в формате: `отдел.регион.тип` (например: `electronics.moscow.retail`, `food.kazan.wholesale` или `clothes.moscow.wholesale`).
3. Создаются два разных воркера:
   * **Воркер 1 (Розничный):** должен обрабатывать *только* розничные заказы независимо от региона и отдела. Маска привязки: `*.#.retail`.
   * **Воркер 2 (Московский):** должен получать *все* заказы, сделанные в Москве. Маска привязки: `*.moscow.*`.

### Чек-лист реализации:
- [ ] В RabbitMQ объявлен обменник типа `ExchangeType.Topic`.
- [ ] Воркер 1 создает очередь и делает `QueueBind` с ключом `*.#.retail`.
- [ ] Воркер 2 создает очередь и делает `QueueBind` с ключом `*.moscow.*`.
- [ ] Протестирована отправка сообщения со специальным ключом `food.moscow.retail`. Убедитесь, что его получили **оба** воркера.

### ❓ Вопросы для самопроверки:
* В чем разница между символами `*` и `#` при настройке масок в Topic Exchange?
* Что произойдет с сообщением, если его Routing Key не совпадет ни с одной из масок у существующих очередей?
